# RFC 0001: Application Signals for Windows

**Status:** Accepted implementable RFC  
**Target platform:** Windows 11 desktop  
**Primary user surface:** Windows GUI  
**Primary agent surface:** local structured subscription/read protocol  
**Primary implementation inputs:** registered filesystem, process/job, application, diagnostic, and UI Automation observations  
**User-visible delivery:** ASW activity UI and optional Windows App SDK notifications

## Abstract

Application Signals for Windows (ASW) is a local Windows service and GUI for useful asynchronous application activity. ASW observes only surfaces authorized by the user; records bounded filesystem, process, job, window, dialog, control, diagnostic, artifact, and application-operation transitions; deterministically reduces eligible observations into structured **signals**; groups signal history by application; lets users and agents subscribe to selected applications and signal categories; delivers user-facing subscriptions through the ASW activity experience and optionally Windows App SDK notifications; and exposes agent subscriptions through a bounded local structured stream with replay cursors.

ASW separates four concerns: **observation authorization**, **observation**, **signal creation**, and **subscription**. A subscription does not grant observation authority and does not create or delete signals. Agents may subscribe only inside the observation scope authorized by the user and inside an explicit user-issued agent access grant.

Signals report what happened. They do not decide what a user or agent should do next.

## 1. Goals

ASW MUST support useful asynchronous signals such as:

- file creation, modification, deletion, or save completion;
- completion or failure of a background process;
- completion of builds, tests, renders, exports, downloads, synchronizations, or similar asynchronous jobs;
- creation of a new application window;
- appearance of a popup, dialog, permission request, or modal surface;
- completion of an application-specific operation;
- availability of a generated artifact;
- changes to diagnostics or other task-relevant application state;
- process crashes, restarts, or unexpected termination;
- activation or availability of a previously blocked UI operation; and
- transitions indicating that work on a registered shared artifact has completed.

ASW MUST also:

1. associate each signal with an application whenever known;
2. maintain replayable local signal history ordered by a durable local journal;
3. present signal history grouped by application in the primary GUI;
4. let users subscribe by application and signal category;
5. let agents subscribe by application and signal category within an explicit access grant;
6. keep observation authorization independent of subscription state;
7. optionally deliver user subscriptions through Windows App SDK notifications;
8. expose bounded structured signal streams and replay cursors to local agents;
9. preserve source reliability and localization uncertainty; and
10. fail closed for unsupported or unauthorized source facts.

## 2. Non-goals

RFC 0001 does not provide:

- universal instrumentation of every Windows application;
- global interception of all Windows notifications;
- arbitrary screenshot semantics or general-purpose visual reasoning;
- general-purpose GUI automation;
- cross-platform support;
- requirement-satisfaction or task-success reasoning beyond narrow source facts;
- automatic recommendations about what to do next;
- agent authority to add folders, processes, applications, or UI surfaces to observation scope;
- multi-machine replication; or
- a mandatory end-user CLI.

## 3. Normative language

**MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** are normative requirements.

## 4. Terminology

### 4.1 Event

An **event** is an observed environmental transition emitted by a source adapter. Events are source facts, not user-facing judgments. An event may be `authoritative`, `observed`, `hint`, or `degraded`.

### 4.2 Signal

A **signal** is a structured ASW record deterministically created from an eligible event or correlated event group after required settling, validation, authorization, correlation, and deduplication.

A signal SHOULD state as many of these facts as are known:

- what happened;
- which application it belongs to;
- which file, artifact, process, job, window, control, dialog, diagnostic source, or application operation was affected;
- when ASW observed it;
- whether the transition represents creation, modification, save completion, deletion, success, failure, crash, restart, availability, blocking, unblocking, or another supported event; and
- the reliability of the underlying source fact.

A signal MUST NOT contain unsupported inferred claims.

### 4.3 Application

An **application** is the primary grouping identity in ASW. It may be identified by package identity, executable identity, or explicit registration. If a supported signal cannot be attributed to a known application, the runtime MUST assign it to the system-defined `unknown` application group instead of silently discarding it.

### 4.4 Observation authorization

**Observation authorization** is user-controlled configuration defining what ASW may observe. It may authorize applications, filesystem roots, processes/jobs, UI Automation surfaces, diagnostics, or application adapter contracts.

Observation authorization MUST be explicit and persisted as authoritative input. An agent cannot create or broaden observation authorization in RFC 0001.

### 4.5 Subscriber

A **subscriber** is a user or agent that may create subscriptions. RFC 0001 subscriber kinds are `user` and `agent`.

A subscriber identity is a routing/access identity only. It is not used to infer who caused an event, who owns an application operation, or whether a signal is relevant by default.

### 4.6 Subscription

A **subscription** selects a subset of the authorized signal universe for one subscriber. A subscription may filter by application, signal category, and optional event type.

Subscriptions MUST NOT:

- create source observations;
- expand observation authorization;
- affect whether a signal is written to canonical signal history; or
- alter another subscriber's subscription state.

### 4.7 Agent access grant

An **agent access grant** is user-issued authorization limiting which applications and categories an agent may read or subscribe to. An agent subscription MUST be a subset of its active access grant and of the user-authorized observation scope.

### 4.8 Signal history

**Signal history** is the replayable local sequence of structured signals produced by the deterministic reducer. Signal history is independent of subscription delivery. Superseded or expired signals may remain replayable even when they are no longer surfaced as current activity.

### 4.9 Frontier

A **frontier** is the ASW-local replay and ordering boundary for observations and signal reducer outputs. It may cite source-specific cursors, epochs, snapshots, or reconciliation identities, but RFC 0001 does not require CRDT state vectors or distributed shared-state frontiers.

For RFC 0001, a frontier is implementation-neutral and local to the Windows observation surface. It does not imply a semantic shared-state model.

Canonical MVP shape:

```json
{
  "journal_sequence": 9188,
  "runtime_epoch": "uuid-runtime-1",
  "source_frontiers": {
    "fs:workspace": {
      "source_epoch": "uuid-fs-3",
      "source_sequence": 42,
      "snapshot_digest": "sha256:optional"
    },
    "uia:registered-windows": {
      "source_epoch": "uuid-uia-2",
      "source_sequence": 17
    },
    "process:task-runner": {
      "source_epoch": "uuid-proc-1",
      "source_sequence": 9
    }
  },
  "reducer_policy_version": "asw.reducer.v1"
}
```

### 4.10 Source reliability

Reliability values are:

- `authoritative`: authoritative for the narrow fact reported;
- `observed`: directly observed, but not authoritative for broader semantics;
- `hint`: preliminary and requiring settling/correlation; and
- `degraded`: completeness or localization cannot currently be guaranteed.

`hint` and `degraded` events MUST NOT become ordinary final signals unless an explicit rule emits a source-health/diagnostic signal.

## 5. Product surface priority

The implementation priority is:

1. **Windows GUI** for observation permissions, applications, subscriptions, activity, and agent access;
2. **local structured agent interface** for subscriptions, reads, streams, and replay cursors;
3. **optional developer/diagnostic CLI** for conformance, debugging, fixture injection, and inspection.

The runtime MUST NOT require normal users or normal agents to manage source registrations through a CLI.

## 6. GUI information architecture

The MVP GUI MUST provide these top-level surfaces or functionally equivalent views:

### 6.1 Activity

Shows signal history grouped by application and sorted by newest signal. It SHOULD support unread/current/history views and category filtering without exposing raw journal internals by default.

### 6.2 Subscriptions

Lets the signed-in/local user configure which applications and categories are surfaced in the ASW activity experience and Windows notification channel.

### 6.3 Applications

Shows observed/available applications, current observation status, source health, and a route to application-specific permissions and subscriptions.

### 6.4 Sources & Permissions

Lets the user authorize, inspect, modify, or revoke observation scope for filesystem roots, processes/jobs, UI Automation, diagnostics, and application adapters.

### 6.5 Agents

Lets the user grant/revoke agent access and inspect each agent's permitted applications/categories. Agent-created subscriptions may be displayed here but agent access grants remain user-controlled.

## 7. Supported event categories

| Category | Event type | Meaning | Typical source |
|---|---|---|---|
| Files | `file.created` | watched file appears | filesystem |
| Files | `file.modified` | watched file changes and stabilizes | filesystem |
| Files | `file.deleted` | watched file disappears | filesystem |
| Files | `file.saved` | registered source reports save completion | application/filesystem |
| Artifacts | `artifact.available` | generated artifact is stable and usable | filesystem/job/application |
| Processes | `process.started` | registered process begins | process |
| Processes | `process.completed` | background process exits successfully | process |
| Processes | `process.failed` | background process exits unsuccessfully | process |
| Processes | `process.crashed` | registered process terminates unexpectedly | process/application |
| Processes | `process.restarted` | registered process restarts | process/application |
| Jobs | `job.completed` | build/test/render/export/etc. succeeds | job/application |
| Jobs | `job.failed` | asynchronous job fails | job/application |
| Windows & UI | `window.created` | new eligible application window appears | UIA |
| Windows & UI | `dialog.appeared` | popup/dialog/permission/modal appears | UIA/application |
| Windows & UI | `operation.available` | previously unavailable registered UI operation becomes available | UIA/application |
| Application | `operation.completed` | registered application-specific operation completes | application |
| Diagnostics | `diagnostic.changed` | registered diagnostics/task state changes | diagnostic/application/job |
| Shared artifacts | `shared_artifact.updated` | registered shared-artifact work reaches reported completion | application/shared source |
| Source health | `source.degraded` | source cannot guarantee complete observation | source |
| Source health | `source.reconciled` | degraded source completes reconciliation | source |

Extensions require versioned schema and reducer-policy updates.

## 8. Observation authorization model

Observation is user authority. The implementation MUST persist authorization separately from source health and subscriptions.

A user MAY authorize:

- an application identity;
- one or more filesystem roots associated with an application;
- specific executable/process identities;
- registered job kinds;
- UI Automation observation for eligible application processes/windows;
- diagnostic adapter contracts; and
- application adapter contracts.

Revoking authorization MUST stop future ordinary observations for that scope after deterministic shutdown/reconciliation bookkeeping. Historical signals MAY remain unless separate retention policy removes them.

Agent APIs MUST NOT expose a method that silently expands observation authorization.

## 9. Subscriber and access model

### 9.1 User subscriptions

User subscriptions may select applications, categories, and optional event types. Supported MVP destinations are:

- `activity_center`; and
- `windows_app_sdk`.

Signal history exists independently of whether a user subscription matches.

### 9.2 Agent subscriptions

An agent may create, update, or delete its own subscriptions through the local agent interface. An agent subscription MUST be checked against:

1. active user observation authorization;
2. the agent's active access grant; and
3. schema-valid application/category/event selections.

An agent MUST NOT receive a signal outside the intersection of those constraints.

### 9.3 Access revocation

Revoking an agent access grant MUST prevent new delivery/read access immediately at the service boundary. Previously returned data cannot be recalled. The runtime SHOULD invalidate or suspend subscriptions that no longer fit the grant.

## 10. Source adapters

### 10.1 Filesystem adapter

The filesystem adapter watches only user-authorized roots. Raw watcher activity is a hint until any required settle/reconciliation completes.

It SHOULD record source ID/epoch, path, event kind, observation time, source-local sequence, size, modified time, digest when required, settle outcome, and reliability.

It MUST emit source degradation when it detects overflow, missed-event conditions, unavailable paths, or reconciliation failure that may affect completeness.

### 10.2 Process/job adapter

The process/job adapter observes only authorized/registered executable and job identities. It SHOULD record application identity, PID, parent relation, job/operation ID, job kind, start/exit time, exit code, and bounded output metadata where policy permits.

### 10.3 UI Automation adapter

UI Automation observation is limited to user-authorized application surfaces. It MAY emit `window.created`, `dialog.appeared`, and `operation.available`. It SHOULD include process/application identity, window metadata, AutomationId/control type where available, physical-pixel bounding rectangles, enabled state, focusability, and localization confidence.

UIA runtime IDs and window handles are ephemeral correlation data, not durable application identity.

### 10.4 Application/diagnostic adapters

Application-specific completion and diagnostic facts require explicit registered adapter contracts. `diagnostic.changed` MUST NOT be synthesized from arbitrary text or screenshots in RFC 0001.

## 11. Settling and artifact availability

Default settle profile:

```yaml
initial_delay_ms: 250
poll_interval_ms: 100
required_stable_observations: 2
maximum_settle_ms: 5000
```

Metadata mode is stable when size and modified time are unchanged for the required stable observations. Digest mode is stable when size and digest are unchanged.

A declared artifact MUST satisfy its configured settle/digest policy before `artifact.available` may be emitted. A settle timeout MUST fail closed and emit an appropriate source/diagnostic fact rather than `artifact.available`.

## 12. Source degradation and reconciliation

A degraded source MUST NOT silently return healthy. The runtime MUST:

1. mark the source degraded;
2. stop promoting incomplete hints into ordinary signals;
3. run deterministic reconciliation over the authorized source scope;
4. compare current state with the last stable snapshot where applicable;
5. record reconciliation observations;
6. advance the source epoch or reconciliation identity; and
7. return healthy only after reconciliation succeeds.

## 13. Deterministic reducer

The reducer maps:

```text
event
+ observation authorization
+ source reliability
+ application identity
+ prior signal state
+ reducer policy version
→ signal update | no-op | source-health signal
```

Subscriptions are deliberately absent from this equation. They filter signal delivery/read views after canonical signal creation.

The reducer MUST NOT call a model, use stochastic classification, infer user intent, or infer task success beyond narrow explicit source facts.

Every signal reducer output MUST be reproducible from authoritative journal inputs, source frontier metadata, observation authorization, application registrations, and the exact reducer-policy version.

## 14. Event and signal contracts

Machine-readable normative contracts are in `schemas/`. The central envelopes are:

```json
{
  "schema_version": "asw.event.v1",
  "event_id": "evt_...",
  "type": "file.saved",
  "application_id": "app.visual-studio",
  "source": {
    "adapter": "application",
    "source_id": "app:visual-studio",
    "source_epoch": "uuid-source",
    "source_sequence": 42,
    "reliability": "authoritative"
  },
  "subject": {
    "kind": "path",
    "value": "C:\\src\\project\\main.cs"
  },
  "observed_at": "2026-08-01T21:27:00-04:00",
  "frontier": {}
}
```

```json
{
  "schema_version": "asw.signal.v1",
  "signal_id": "sig_...",
  "derived_from": ["evt_..."],
  "application_id": "app.visual-studio",
  "category": "files",
  "kind": "file.saved",
  "status": "current",
  "subject": {
    "kind": "path",
    "value": "C:\\src\\project\\main.cs"
  },
  "source_reliability": "authoritative",
  "frontier": {}
}
```

## 15. Signal history, correlation, deduplication, supersession

ASW owns replayable signal state, not the underlying application state.

Deterministic correlation keys MAY include application ID, source ID, path/artifact key, PID/job ID, operation ID, window correlation fields, digest, settle result, or registered relationship.

Duplicate source events may be journaled without producing duplicate signals. Newer signals may supersede older signals for the same deterministic subject key. Superseded/expired signals remain replayable metadata unless retention removes them.

## 16. Journal authority and rebuildable state

Authoritative journal inputs include:

- application registrations;
- observation authorizations;
- source registrations and health/reconciliation facts;
- source events;
- subscriber registrations;
- agent access grants and revocations;
- subscriptions and subscription changes;
- reducer-policy versions; and
- delivery attempts/results where auditing is required.

Derived/rebuildable state includes:

- normalized signal projections;
- active/current views;
- application-grouped GUI projections;
- subscription match indexes;
- agent stream indexes;
- SQLite indexes/caches; and
- replay acceleration structures.

Deleting a derived index MUST NOT alter semantic state.

## 17. Frontier and replay

The durable local `journal_sequence` is the principal ASW ordering boundary. `runtime_epoch` prevents restart ambiguity. Each source may maintain a `source_epoch`, source-local sequence/cursor, and snapshot/reconciliation identity.

A replay cursor MUST survive service restart because it identifies a durable journal position plus the runtime/source metadata needed to detect discontinuity. Replay MUST reconstruct ASW signal state only; it MUST NOT re-execute processes, rewrite files, or replay UI actions.

## 18. Agent interface

The agent interface is local, structured, bounded, and transport-neutral. Named pipes, local HTTP/WebSocket, or another local IPC binding MAY implement the same contract.

Required logical operations:

```text
get_capabilities
list_applications
get_access_grant
list_subscriptions
create_subscription
update_subscription
delete_subscription
list_signals
get_signal
open_signal_stream
resume_signal_stream
```

Responses MUST include a replay cursor/frontier where applicable and MUST enforce the agent access grant server-side.

The agent interface MUST NOT require use of the developer CLI.

## 19. Developer/diagnostic CLI

A CLI MAY exist for conformance and troubleshooting. It is not a primary product surface. It MAY support schema validation, fixture injection, journal inspection, replay verification, source health diagnostics, and index rebuilds.

CLI commands are deliberately non-normative in RFC 0001 so the implementation is not coupled to a command vocabulary.

## 20. Windows GUI behavior

### 20.1 Application grouping

The Activity view MUST group signals by application. Within an application group, default ordering is newest first. The GUI MAY provide alternate category/time filters.

### 20.2 Subscription editing

The GUI MUST let users select applications and categories without exposing internal reducer policy. It SHOULD show plain-language categories such as Files, Jobs, Diagnostics, Artifacts, and Windows & UI.

### 20.3 Permission editing

Filesystem/process/UI observation changes MUST be presented as user authorization decisions, not as notification preferences. The UI SHOULD clearly distinguish "Observe" from "Notify me".

### 20.4 Agent access

The Agents view MUST show which applications/categories each agent may access and MUST provide a user-controlled revoke action.

## 21. Windows notification delivery

Windows App SDK notifications are a user delivery channel, not signal authority.

A delivered Windows notification MAY contain a title, bounded summary, application identity, supported actions, expiry, and an activation reference to the ASW signal ID.

Delivery failure MUST NOT delete or invalidate the signal. Failure is recorded separately and the signal remains available in Activity/history and to authorized agent subscribers.

## 22. Coordinate payload

UI locations use `windows_virtual_screen_physical_px`. Coordinate payloads SHOULD include virtual-screen rectangle, monitor rectangle/DPI where available, window and element rectangles, visibility, enabled/focusable state, localization confidence, frontier, and ephemeral UIA correlation data.

Coordinates are observed localization data and MUST preserve uncertainty.

## 23. Conformance scenarios

The MVP MUST test at least:

1. Stable file creation produces one signal.
2. Multiple modifications during settling produce one final useful signal where policy says they coalesce.
3. Unauthorized filesystem paths produce no ordinary signal.
4. Save completion reported by an authorized source becomes `file.saved`.
5. Registered job success produces `job.completed`.
6. Registered job failure produces `job.failed`.
7. Stable generated artifact produces `artifact.available`; unstable artifact never does.
8. Eligible window creation includes physical-pixel location when available.
9. Eligible dialog appearance produces a signal without inferred workflow semantics.
10. Previously unavailable registered UI operation becoming enabled produces `operation.available`.
11. Filesystem overflow produces `source.degraded` and reconciliation before health restoration.
12. Canonical signals are created independent of whether any subscription matches.
13. User subscription filters user delivery without altering signal history.
14. Agent subscription filters agent delivery without altering signal history.
15. Agent subscription outside its access grant is rejected.
16. Agent request for an application outside its access grant returns no signal data.
17. Revoking an agent grant stops subsequent reads/streams.
18. Windows notification delivery failure leaves the signal in history.
19. Replay reconstructs materially equivalent signals without external side effects.
20. Index/cache deletion followed by rebuild leaves semantic state unchanged.
21. Invalid/unsupported schema versions fail closed.
22. Degraded or hint-only facts do not become ordinary final signals.

## 24. Evaluation

Comparative evaluation SHOULD include at least:

- polling-based observation;
- filesystem watching alone;
- ordinary Windows notification text;
- repeated visual observation; and
- ASW structured signals.

Metrics SHOULD include observation count, time to correct continuation, attribution accuracy, false-positive signal rate, missed-signal rate, duplicate rate, continuation success, and agent tool/token cost.

Evaluation profiles MUST be predeclared before comparative runs.

## 25. MVP completion criterion

RFC 0001 is complete only when every requirement in `checklists/MVP_COMPLETION_CHECKLIST.md` has passing evidence. The checklist is a hard release gate, not a roadmap.
